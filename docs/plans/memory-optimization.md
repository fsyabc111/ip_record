# IP Record 内存优化规划

日期：2026-11-08（Asia/Taipei）。状态：仅规划，尚未实施。

本轮只编写并推送本规划及文档入口。下述构建、测量、代码修改、测试和安装均为后续工作，本轮不执行，不影响正在运行的应用或正式历史。

## 1. 目标与范围

在保持封版 v1.0 产品范围和正确性合同的前提下，定位内存增长来源，降低可控的常驻占用和临时峰值，并验证长期运行是否稳定。

沿用原有目标：

| 项目 | 验收目标 |
| --- | --- |
| 后台内存 | 窗口全部关闭、网络稳定时，稳态 RSS ≤80 MiB；分别验证首次启动和使用界面后返回后台 |
| 窗口内存 | 历史／设置窗口打开时，稳态 RSS ≤150 MiB；另外报告操作峰值 |
| 内存稳定性 | 界面反复开关、分页、导出及取消后，对象数量和占用曲线趋于稳定，无持续累积 |
| CPU | 窗口关闭、网络稳定时，10分钟单逻辑核心 CPU 均值 ≤0.2% |
| 响应 | 菜单打开目标 ≤200 ms；十万条合成历史的完整界面首屏目标 ≤500 ms |
| 记录正确性 | 双族独立确认、过期轮次隔离、存储故障停止探测、不可变首次快照和暂停意图保持不变 |

RSS、physical footprint、堆分配、文件映射分别记录；physical footprint 不替代 RSS 验收。目标暂不调整，优化收益必须来自同条件测量。

## 2. 已知事实与证据边界

本规划核对的源码基线为 `3aee741`。

| 现有证据 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 早期构建采样约30分钟，60秒后 RSS 为73.75–136.53 MiB | 当时运行出现过高于80 MiB目标的占用 | 不能当作最终构建、纯后台隔离复测结果 |
| 最后 physical footprint 约48.80 MiB | 与 RSS 是不同的内存指标 | 不能据此把 RSS 预算标为通过 |
| 采样期间有原生界面／辅助功能检查并行发生 | 测量条件存在混合，增长时段需要重新隔离 | 尚未确认增长由框架缓存、应用持有对象或其他原因导致 |
| 现有记录为34项自动化测试通过 | 提供后续优化的功能回归基线 | 本规划没有重跑测试，也不证明资源目标已通过 |

现有30分钟采样二进制 SHA-256：`3f239223b10f7e6805ff1fad72ae95394821bdaa94493f54d43dad6ffb651929`。后续报告必须记录各自的源码提交和二进制哈希，避免跨构建混用结果。

源码已具备以下措施，后续首先验证其效果，不重复计作新增优化：

- `GeoResolver` 使用 C 文件读取模式，归属缓存上限128条；流式哈希的每块读取置于 `autoreleasepool` 中。
- 每次 C 查询以 `defer` 释放 region buffer，C句柄由串行所有者管理。
- popover 关闭后解除内容控制器；历史／设置窗口关闭后清除 SwiftUI 内容，窗口壳仍保留用于复用。
- 历史查询默认每页100条；导出按最多500条一批写入，不一次读取全部历史。

另有需要纳入验证的源码事实：历史列表当前取得完整 `HistoryRecord`，会解码首次快照；“加载更多”通过追加数组保留此前加载的记录。这是规模优化的明确检查点，但不是136.53 MiB峰值的已证实根因。

## 3. 执行原则

1. 先建立能捕获用户所见内存问题的反馈，再确定根因；没有可重复证据时，不批量修改代码。
2. 短循环用于定位对象释放和操作增量，30分钟运行用于最终验收，二者分别报告。
3. 一次改变一个主要因素，保留优化前后可比较的构建和结果。
4. 保持单进程、现有原生界面、记录频率、长期历史及数据库可信校验；遵守全部已确认语义。
5. 使用隔离数据和测试偏好，不修改正式历史、登录项或日常网络配置。测试实例与正式实例通过独立身份和数据目录区分，避免工具选错进程。
6. 原始诊断文件保存在本地忽略的 `.artifacts/`；提交报告仅包含脱敏后的计数、资源指标和必要引用。

## 4. P0：建立隔离基线和反馈循环

### 测量准备

- 固定同一份 arm64 release 构建，记录提交、二进制哈希、签名、系统及工具链版本。
- 每个场景从全新测试进程开始，记录 PID、隔离目录、启动方式和操作时间点。
- 纯后台测量不连接辅助功能工具，不使用会自动打开历史／设置的 `--self-check` 作为后台基线。
- 交互、辅助功能和性能分析工具的测量分开进行；同一被测进程不并行接受多套操作。
- 先用固定模拟输入隔离应用对象的变化，再单独验证真实网络；模拟数据不冒充真实网络结果。

### 场景矩阵

| 编号 | 场景 | 观察重点 |
| --- | --- | --- |
| M01 | 已完成首次说明的纯后台进程，至少30分钟 | 启动峰值、稳态、定时检查前后增量 |
| M02 | 首次打开菜单，关闭后继续观察 | 首次界面成本及关闭后的保留量 |
| M03 | 打开历史、设置，全部关闭后继续观察至少30分钟 | 分别记录各窗口增量及返回后台的稳态 |
| M04 | 菜单／历史／设置分别反复开关50次 | 区分首次加载台阶、稳定缓存和逐轮增长 |
| M05 | 十万条合成历史，首屏、连续分页、选中详情和切换筛选 | 列表对象、完整快照和页缓存占用 |
| M06 | 大范围导出、取消、失败及重试 | 批次峰值、临时对象和读连接释放 |
| M07 | 重复探测成功／失败、取消、暂停与恢复、模拟网络事件 | 请求、任务和状态发布是否累积 |
| M08 | 在单独运行中连接辅助功能工具并重复操作 | 工具介入前后增量，不能混入M01结论 |

短循环应自动输出操作前、预热后、若干轮操作后及静置后的指标。先确认它能稳定捕获超预算或对象累积；若只能在长运行中复现，明确保留长循环，不宣称短测试已覆盖。

每个场景记录 RSS、physical footprint、堆占用、映射分类、CPU、线程／文件描述符数量，以及应用检查轮数和分族探测尝试数。Mach时间计数按本机timebase转换。

**阶段出口：** 得到带构建身份的基线表、可重放步骤，以及能区分首次加载与持续增长的曲线。P0不承诺已经确定根因。

## 5. P1：定位持有者和增长来源

基于P0的增长时段，再生成可证伪的假设和对应探针；以下仅是检查范围，不预先认定其中任何一项存在泄漏。

| 范围 | 待检查内容 | 后续修改的证据条件 |
| --- | --- | --- |
| 窗口与SwiftUI内容 | window、hosting view/controller、历史模型、视图树在关闭后是否按预期释放 | 对象存活或引用链表明确实保留了不再需要的内容 |
| 异步任务与订阅 | 查询、详情、状态发布、导出和通知回调的生命周期；窗口关闭、快速切换及面板停留时的积压 | 被取消或过期操作仍持有快照、模型或连接，或任务数量持续增长 |
| 历史与编码 | 完整快照解码、行数组累计、SQL结果字符串及JSON对象的同时存活量 | 分配差异能归因于具体页、快照或转换路径 |
| 网络和归属 | URLSession、任务、C buffer、文件句柄与有界缓存 | 多轮请求／查询后存活数量增长，或释放时间异常 |
| 系统框架与分配器 | 首次UI／辅助功能加载的映射、可复用堆页和业务活跃对象 | 可以区分框架映射台阶与应用仍然持有的数据 |

先采用当前CLT环境可用的工具。需要其他分析工具时先核实可用性，不能把尚未安装的完整Xcode或某个分析器当作已具备条件。

**阶段出口：** 一份“已证实原因／已排除项／仍不确定项”列表，每项关联场景、指标和引用链或分配证据；只有已证实或能单独验证的修改进入实施。

## 6. P2：优先改进历史列表的内存边界

这一阶段针对已确认的列表数据结构，收益仍须测量，不等同于已解决后台峰值。

1. 列表只读取显示与筛选需要的摘要；选中后按ID读取完整首次快照及确认摘要。优先利用现有字段或按需投影，确需迁移时按设计先备份。
2. 为已加载摘要页设置明确缓存上限。500–1000条可作为待验证起点，不是新的封版指标；根据占用和响应选择最终值。
3. 较早页面通过游标重新读取，保持向前／向后浏览、滚动位置、选择和筛选语义，不丢失历史访问能力。
4. 详情及上一条比较快照只保留当前需要的数据，窗口关闭或选择变化时取消过期读取。
5. 查询、筛选和取消保持有限中间结果，避免完整JSON字符串与解码对象不必要地同时长时间存活。

**验收：** 十万条测试库的界面首屏和连续浏览均可用；已加载业务数据受缓存上限约束；页数增加不导致全部历史快照常驻；详情、稳定ID顺序、复制和导出内容保持一致。

## 7. P3：按证据处理其他生命周期与峰值

只实施P1有依据的项目：

- 若关闭窗口后仍保留视图或模型，修正持有关系、任务取消和清理时点；维持窗口单实例与复用体验。
- 若主线程繁忙时UI状态任务积压，考虑有界的最新状态传递，保留版本校验；历史写入及生命周期标记仍由记录引擎完整处理。
- 若JSON、字符串或系统配置桥接产生明显临时峰值，缩小对象作用域并减少重复转换；必要时在同步批次边界使用 `autoreleasepool`，不跨异步挂起点使用。
- 若会话或读连接释放异常，修正其所有权；网络上下文改变后的取消／重建、禁用HTTP缓存、拒绝交互认证等合同保持有效。
- 若原生缓冲或句柄出现问题，修复后补充对应压力与内存安全检查；归属缓存继续有界，可信校验在进入C读取器前完成。

每项修改均用相同场景比较前后RSS、footprint、对象数量、CPU和响应；没有可重复收益或造成回归的修改撤回。

## 8. P4：回归、最终验收与交付

### 功能与资源回归

- 重跑现有34项测试，并按实际修改补充对象释放、过期任务、分页缓存、详情读取、导出取消等有意义的回归。
- 受影响的原生读取路径重新进行压力和内存安全验证；内存安全工具未报错不等同于长期无泄漏。
- 检查双族失败时间、epoch隔离、只变化追加、不可变首次快照、清空保留当前、暂停和存储故障等关键不变量。
- 验证窗口关闭继续记录、同一窗口复用、键盘操作、完整地址复制，以及导出的首次快照／摘要合同。

### 最终测量

- 使用最终候选构建重跑M01和M03，分别完成至少30分钟验证；交互操作结束后，返回后台的观察时间独立计算。
- 完成M04的50次开关及M05–M07专项循环，记录峰值和静置后的稳定区间。
- 至少补一次独立重复运行检查结果是否可复现；异常网络事件、辅助功能介入等条件单独标注。
- 同时检查CPU、请求尝试数、响应和存储，避免内存收益伴随能耗、联网或记录行为回归。
- 不把旧构建的34项测试或早期资源数据作为最终构建新测量的替代。

**完成条件：** 资源目标在对应条件下通过，曲线无持续累积，功能回归通过，证据能追溯到最终构建。若确认系统框架等开销仍使RSS超标，记录内存分类、已取得收益和剩余差距，保持该门“未通过”，再单列可选方案，不静默放宽目标或改变封版语义。

### 交付物

1. 优化前后对照报告：构建身份、场景、操作次数、峰值／稳态、CPU、占用分类及不确定项。
2. 可复现的测量驱动和必要回归测试，原始隐私数据仅保存在隔离本地目录。
3. 更新后的验收报告，分别列出自动化、模拟、真实网络、实际界面和仍待人工项。
4. 已验证的应用产物与分阶段提交；安装替换按现有约定进行，保护正式历史和设置。

## 9. 实施与提交顺序

| 阶段 | 预期提交内容 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0–P1 | 测量驱动、脱敏基线、复现与定位证据 | 有可重复反馈及明确检查结论 |

阶段可根据定位结果合并或省略无必要的修改，不为凑提交次数拆分。每个有意义的阶段按项目约定提交并及时推送，推送后核对本地与远程；尚未完成的验证明确标注。
